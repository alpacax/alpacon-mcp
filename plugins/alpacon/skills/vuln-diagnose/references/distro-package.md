# Distribution packages

The advisory names a source package (`openssh`) and a fixed version per release. Check the binary packages the server actually installs (`openssh-server`, `openssh-client`); every binary built from that source carries the same version once upgraded, but a server can hold them at different versions. When the advisory does not say which binary carries the vulnerable code, run the check once per binary, setting `p` in the commands below. A server's verdict is the worst of its checks: `affected` over `unknown` over `not_affected`.

Each check is one shell line and runs as an ordinary account; none of these commands needs root. The checks read `/etc/os-release` with `sed` instead of sourcing it, and use no `$(…)` command substitution or `${…}` parameter expansion. In one experiment Alpacon's approval gate raised a read-only check with those three from INFO to MEDIUM or HIGH; the checks below have not been graded since. Keep that shape when you edit a check, and fill in only its values.

## Debian and Ubuntu

`dpkg --compare-versions` orders Debian versions (epochs, `~`, revisions) correctly on the host, so the host decides the verdict. Set `p` to the binary package and fill in one `case` arm per release from the distribution's tracker. A release the tracker lists as vulnerable with no fixed package yet gets `f=none` (`focal` below is such an arm), so an installed copy reports `reason=no-fix-available` instead of a version comparison:

```sh
p=openssh-server; { sed -n 's/^VERSION_CODENAME=/Release: /p' /etc/os-release | tr -d "\"'"; dpkg-query -s "$p" 2>/dev/null; echo "Exit: $?"; } | grep -E '^(Release|Status|Version|Exit): ' | { while read -r k a b c; do case "$k" in Release:) r=$a;; Status:) w=$a; x=$b; s=$c;; Version:) v=$a;; Exit:) e=$a;; esac; done; case "$r" in jammy) f='1:8.9p1-3ubuntu0.10';; noble) f='1:9.6p1-3ubuntu13.5';; focal) f=none;; *) echo "verdict=unknown release=$r reason=release-not-in-advisory"; exit 0;; esac; case "$w" in install) t=i;; hold) t=h;; deinstall) t=r;; purge) t=p;; *) t=u;; esac; case "$s" in installed) t="$t"i;; not-installed) t="$t"n;; config-files) t="$t"c;; unpacked) t="$t"U;; half-installed) t="$t"H;; half-configured) t="$t"F;; triggers-awaited) t="$t"W;; triggers-pending) t="$t"t;; esac; [ "$x" != reinstreq ] || t="$t"R; case "$e:$s" in 0:installed) ;; 0:not-installed|0:config-files) echo "verdict=not_affected package=$p release=$r installed=none status=$t"; exit 0;; 1:) echo "verdict=not_affected package=$p release=$r installed=none"; exit 0;; *) echo "verdict=unknown package=$p release=$r reason=dpkg-query-exit-$e status=$t"; exit 0;; esac; [ "$f" != none ] || { echo "verdict=affected package=$p release=$r installed=$v status=$t reason=no-fix-available"; exit 0; }; dpkg --compare-versions "$v" lt "$f"; case $? in 0) o=affected;; 1) o=not_affected;; *) echo "verdict=unknown package=$p release=$r installed=$v status=$t reason=unorderable-version"; exit 0;; esac; echo "verdict=$o package=$p release=$r installed=$v fixed=$f status=$t"; }
```

The check prints dpkg's status abbreviation as `status=`, rebuilt from the `Status:` line `dpkg-query -s` prints: two letters, and a third `R` when dpkg marks the package for reinstallation. A package `dpkg-query` does not know has no `Status:` line, so its row has no `status=`. The second letter is what is on disk: `i` is installed, whatever the first letter says, so a held package (`hi`) counts, and it is exactly the kind that missed an upgrade. An `affected` row with `status=hi` is held: the remediate recipe cannot upgrade it until a person releases the hold. `n` and `c`, or exit 1 with no output, mean not installed. Anything else, a half-installed package or a package database `dpkg-query` cannot read, is `unknown`.

A package installed for two architectures (`libssl3:amd64` and `libssl3:i386`) is `unknown` with `reason=dpkg-query-exit-2`, because `dpkg-query` refuses the bare name as ambiguous; set `p` to `<package>:<arch>` and run the check once per architecture.

## RHEL, Rocky, AlmaLinux, Fedora

The repositories' update metadata already maps a CVE to the advisory that fixes it, so the check asks `dnf` instead of comparing RPM versions by hand. Keep only the advisory lines for the package being checked:

```sh
c='CVE-2099-0001'; p=openssh-server; { sed -n 's/^ID=/id /p; s/^VERSION_ID=/version_id /p' /etc/os-release | tr -d "\"'"; rpm -q rpm >/dev/null 2>&1; echo "rpmdb $?"; LC_ALL=C rpm -q --qf 'version %{EPOCHNUM}:%{VERSION}-%{RELEASE}\n' "$p" 2>/dev/null; echo "rpm $?"; for q in available installed; do { dnf -q updateinfo list --"$q" --cve "$c" 2>/dev/null; echo "exit $?"; } | sed "s/^/$q /"; done; } | awk -v n="$p" 'BEGIN {p = n "-"} $1 == "id" {id = $2} $1 == "version_id" {vid = $2} $1 == "rpmdb" {db = $2} $1 == "version" {v = v (v == "" ? "" : " ") $2} / is not installed$/ {absent = 1} $1 == "rpm" {re = $2} ($1 == "available" || $1 == "installed") && $2 == "exit" {x[$1] = $3; next} ($1 == "available" || $1 == "installed") && index($4, p) == 1 && substr($4, length(p) + 1, 1) ~ /[0-9]/ {hit[$1] = 1} END {h = "package=" n " release=" id "-" vid; if (db != 0) {print "verdict=unknown " h " reason=rpm-database-unreadable"; exit} if (re != 0) {print (absent ? "verdict=not_affected " h " installed=none" : "verdict=unknown " h " reason=rpm-exit-" re); exit} r = x["available"] != 0 ? "unknown" : hit["available"] ? "affected" : x["installed"] != 0 ? "unknown" : hit["installed"] ? "not_affected" : "unknown"; print "verdict=" r " " h " installed=" v}'
```

An unreadable RPM database answers "not installed" for every package, so the check first asks for `rpm` itself. `--available` lists a fixing advisory not yet installed; `--installed` lists one already installed. Do not pass the package name to `dnf updateinfo` itself: with a package argument it also lists that package's unrelated advisories. A failed query is `unknown`, even when the other query could name an installed advisory. Neither list naming the package means the repositories carry no update metadata for that CVE (CentOS Stream, a mirror without it, or a repository the server cannot reach), so the verdict is `unknown`, and the report says to compare `installed` with the advisory by hand.

## The kernel

What matters is the running kernel, not the newest one installed. A server running an old kernel with a fixed one installed is `affected` with `reason=reboot-pending`: it needs a reboot, not a patch, and `vuln-verify` reads that reason.

Ubuntu keeps the ABI name (`6.8.0-45-generic`) across some updates, so `uname -r` cannot tell two builds apart. Read the running build from `/proc/version_signature` (`Ubuntu 6.8.0-45.45-generic 6.8.12`) instead.

Ubuntu builds each kernel flavour (`generic`, `lowlatency`, `aws`, `azure`, `gcp`, `oracle`) from its own source package with its own version numbers: the fixed `aws` build `6.8.0-1015.16` is not comparable with the fixed `generic` build `6.8.0-45.45`. Each kernel series is tracked separately as well: a release ships its own series and, through hardware enablement (HWE), later ones (`6.8.0-45.45~22.04.1` on jammy; `6.11` and `6.14` on noble), and a fix in one series says nothing about another. So the check reads the running flavour and series (`6.8.0`), and takes the fixed version for that combination from the USN; a combination the USN does not list is `unknown`, never compared against another flavour's or series' version. Fill in one `case` arm per release, flavour, and series the USN lists, and `f=none` for one it lists as still vulnerable:

```sh
{ sed -n 's/^VERSION_CODENAME=/Release /p' /etc/os-release | tr -d "\"'"; sed -n 's/^[^ ]* \(\([0-9.]*\)-[0-9.]*\(~[0-9.]*\)\{0,1\}\)-\([a-z][^ ]*\)\( .*\)\{0,1\}$/Running \1 \4 \2/p' /proc/version_signature 2>/dev/null; } | { while read -r w a b c; do case "$w" in Release) r=$a;; Running) v=$a; k=$b; t=$c;; esac; done; [ -n "$v" ] || { echo "verdict=unknown reason=no-version-signature"; exit 0; }; case "$r:$k:$t" in noble:generic:6.8.0) f='6.8.0-45.45';; noble:aws:6.8.0) f='6.8.0-1015.16';; jammy:generic:6.8.0) f='6.8.0-45.45~22.04.1';; noble:generic:6.14.0) f=none;; *) echo "verdict=unknown running=$v flavour=$k series=$t reason=flavour-not-in-advisory"; exit 0;; esac; [ "$f" != none ] || { echo "verdict=affected running=$v flavour=$k series=$t reason=no-fix-available"; exit 0; }; if dpkg --compare-versions "$v" ge "$f"; then echo "verdict=not_affected running=$v flavour=$k fixed=$f"; exit 0; fi; dpkg-query -l "linux-image-$t-[0-9]*-$k" 2>/dev/null | awk '$1 ~ /^.i/ {print $3}' | { g=; while read -r i; do dpkg --compare-versions "$i" ge "$f" && g=1; done; if [ -n "$g" ]; then echo "verdict=affected running=$v flavour=$k fixed=$f reason=reboot-pending"; else echo "verdict=affected running=$v flavour=$k fixed=$f"; fi; }; }
```

`reboot-pending` counts only an installed image of the running series and flavour (`linux-image-<series>-<abi>-<flavour>`), so a fixed `generic` image installed beside a running `aws` kernel does not make the `aws` server look fixed after a reboot.

- Debian: every flavour (`amd64`, `cloud-amd64`, `rt-amd64`) is built from the one `linux` source package, so one fixed version per release covers them. The running build is in `uname -v` (`... Debian 6.1.112-1 (2024-09-30)`); read it with `uname -v | sed -n 's/.* Debian \([^ ]*\) .*/\1/p'` and compare the same way.
- RHEL family: `uname -r` (`5.14.0-427.13.1.el9_4.x86_64`) names the build. Kernel release strings are numeric, so `printf '%s\n' "$running" "$fixed" | sort -V | head -1` gives the older one, and `rpm -q --qf '%{VERSION}-%{RELEASE}.%{ARCH}\n' kernel-core` lists the installed ones for the `reboot-pending` case. A real-time kernel (`+rt` in `uname -r`, package `kernel-rt-core`) has its own fixed version in the RHSA; without one it is `unknown`. `dnf updateinfo` looks at installed packages, not the running kernel, so do not use it here.
